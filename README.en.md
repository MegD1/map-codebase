# map-codebase

[简体中文](./README.md) | [English](./README.en.md)

`map-codebase` is a Codex Skill for generating interactive architecture maps from real codebases.

It reads source code, turns code subsystems into scalable, pannable, inspectable isometric buildings, and draws evidence-backed call relationships as routes across the map. Moving light points represent real data snippets traveling along those routes. You can pause the flow, trace it one step at a time, and inspect each payload.

![map-codebase interactive architecture atlas preview](./assets/preview.jpg)

## What it does

- Identifies code subsystems across entry points, routes, servers, background jobs, data layers, tests, and deployment scripts.
- Sizes modules from measured files and lines of code instead of handwritten metrics.
- Records source evidence paths for every connection between modules.
- Extracts user flows, background flows, and release flows from the source.
- Creates inspectable payload snippets for each flow.
- Supports module and file search, zoom, pan, pause, resume, step tracing, and view reset.
- Copies discussion context for a selected module or flow so you can continue exploring it with Codex or another AI.
- Generates a stable fingerprint and detects drift between the codebase and its architecture map with `--check`.
- Supports keyboard navigation, responsive layouts, and `prefers-reduced-motion`.

## Visual encoding

The Atlas represents code structure as isometric buildings.

| Code characteristic | Visual representation |
|---|---|
| One dense source file | A tall monolithic tower |
| Several files sharing one responsibility | A layered module |
| Many parallel files | A sliced array |
| A horizontal rendering or transformation pipeline | A wide, low slab |
| Lines of code | Module footprint and height |
| File count and average file density | Module form, layers, and slice count |
| Calls, writes, responses, or release relationships | Isometric ground routes |
| Requests, records, feeds, generated results, or artifacts | Inspectable light points moving along routes |

ASCII dots, `0`, `1`, `+`, and `:` are used only as deterministic textures on code blocks. The background does not generate decorative particle clouds, neural networks, or motion unrelated to the codebase.

## Working principles

### Humans interpret semantics; scripts measure scale

Module responsibilities, implementation notes, flows, and payloads require an understanding of the source. File counts, lines of code, byte counts, coverage, and content fingerprints are generated by the synchronization script.

### Draw only evidence-backed connections

Every edge must reference at least one source path that exists. When a request and response carry different data, model them as two directional connections.

### One file belongs to one module

The synchronization script checks for overlapping and unassigned files. Collaboration between modules is represented through edges rather than by assigning the same file to multiple nodes.

### Motion must carry information

Every moving light point must represent a real data shape, such as an HTTP request, database record, feed, generated result, or release artifact. Decorative motion does not belong in the Atlas.

## Installation

Clone the repository and copy it into your Codex Skills directory:

```bash
git clone https://github.com/MegD1/map-codebase.git
mkdir -p ~/.codex/skills
cp -R ./map-codebase ~/.codex/skills/map-codebase
```

For Skill development, use a symbolic link so local changes take effect without copying the directory again:

```bash
mkdir -p ~/.codex/skills
ln -s "$(pwd)/map-codebase" ~/.codex/skills/map-codebase
```

Open a new Codex task and invoke `$map-codebase`.

## Usage

Ask Codex from the repository you want to analyze:

```text
Use $map-codebase to generate an interactive architecture map for this repository.
```

You can focus the analysis on specific concerns:

```text
Use $map-codebase to map this repository.
Focus on the core write flow, background jobs, data layer, and production release path.
```

To update an existing Atlas:

```text
Use $map-codebase to update the existing architecture map.
Preserve node positions and flow order, and update only the modules and relationships that changed.
```

## Files generated in the target repository

By default, the Skill creates:

```text
atlas/
├── index.html
├── atlas.css
├── atlas.js
├── atlas.config.json
├── data.generated.js
└── measurements.generated.json

scripts/
└── sync-atlas.mjs
```

- `atlas.config.json` is the human-authored system model containing groups, nodes, edges, flows, and payloads.
- `measurements.generated.json` contains the complete generated measurements.
- `data.generated.js` exposes the same generated data directly to the browser.
- `sync-atlas.mjs` scans files, measures the codebase, validates ownership, and detects drift.

## Recommended project commands

Add the following scripts to the target repository's `package.json`:

```json
{
  "scripts": {
    "atlas:sync": "node scripts/sync-atlas.mjs --root .",
    "atlas:check": "node scripts/sync-atlas.mjs --root . --check"
  }
}
```

Generate or refresh measurements:

```bash
npm run atlas:sync
```

Check whether the Atlas still matches the current source:

```bash
npm run atlas:check
```

`atlas:check` fails when:

- controlled source files remain unassigned;
- a file belongs to more than one module;
- an edge references a source path that does not exist;
- generated output no longer matches the current source fingerprint.

## Configuration model

`atlas/atlas.config.json` contains these top-level fields:

| Field | Purpose |
|---|---|
| `meta` | Product name, repository name, title, description, and version |
| `sources` | Source globs included in measurements |
| `ignore` | Dependencies, build artifacts, runtime data, and sensitive paths to exclude |
| `groups` | System regions and their spatial positions |
| `nodes` | Subsystem responsibilities, source ownership patterns, and positions |
| `edges` | Directional relationships backed by source evidence |
| `flows` | Ordered call paths and inspectable payloads |

See [`references/schema.md`](./references/schema.md) for the field reference and [`references/authoring.md`](./references/authoring.md) for modeling guidance.

## Security boundaries

The synchronization script outputs file paths and measurements. It does not write source file contents into generated artifacts.

Explicitly exclude:

- `.env` and other credential files;
- cookies, browser sessions, and authentication caches;
- databases and runtime data;
- user uploads;
- build output and dependency directories;
- complete internal prompts or production data samples.

Payload examples should use placeholder values instead of real credentials, personal content, or production records.

## Validation

Validate the Skill structure and metadata with the official validator:

```bash
python3 /path/to/skill-creator/scripts/quick_validate.py .
```

The repository has no third-party runtime dependencies, so you can also run its package check directly:

```bash
npm run check
```

Before publishing or handing off an Atlas:

1. Run the target repository's syntax, type, lint, and test commands.
2. Run `atlas:check`.
3. Inspect every flow, module, payload, and search result.
4. Verify pause, step, zoom, pan, and keyboard interactions.
5. Check desktop, tablet, mobile, and reduced-motion modes.
6. Confirm that generated files contain no sensitive information.

## Good use cases

- Helping new contributors understand an unfamiliar codebase.
- Discussing a specific module or call path with Codex.
- Mapping system boundaries before a refactor.
- Tracing request or background-job data flows.
- Architecture reviews and technical presentations.
- Detecting when architecture documentation drifts as the code grows.

`map-codebase` does not replace the source. It gives the source a shared spatial model that people and AI can observe, locate, and discuss together.
